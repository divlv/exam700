# Развёртывание AZ-700 Exam Trainer на K3s

## Зачем это нужно

Веб-версия тренажёра AZ-700 позволяет заниматься с любого устройства — ноутбука,
планшета или телефона — без установки десктопного приложения. Контейнер
собирается автоматически в GitHub Actions при каждом push в `main` и
публикуется в `ghcr.io/divlv/exam700`. Разворачивается он на вашем личном
K3s-сервере (`myk3s`, `37.27.214.42`) как обычный под в namespace `mywebs`,
рядом с остальными вашими сайтами, по HTTPS через Traefik.

База данных (SQLite) и картинки вопросов/ответов (169 МБ) хранятся не в
образе, а на диске сервера — в `/data/az700`, по той же схеме, что уже
используется для ваших других приложений (`/data/zaharov-info`,
`/data/postgres` и т.д.). Это значит, что образ маленький и публичный, а
статистика сессий переживает любое обновление приложения.

Манифесты лежат в `deploy/k3s/` этого репозитория. Каждый файл ниже — это то,
что вы применяете вручную командой `k3s kubectl apply -f <файл>`.

## Что понадобится заранее

- SSH-доступ к серверу (`root@37.27.214.42`).
- Доступ к панели вашего DNS-регистратора, чтобы завести A-запись.
- Локальная копия датасета: `sample/data/az700.sqlite` и `sample/data/images/`
  из этого репозитория (369 вопросов, 738 картинок).

## Шаг 1. DNS-запись

Заведите A-запись `az700.v1.lv` → `37.27.214.42` и дождитесь её
распространения:

```cmd
nslookup az700.v1.lv
```

Это нужно сделать **до** применения Ingress (шаг 5): Traefik проверяет право
на домен через HTTP-запрос (ACME HTTP-01), и без готовой DNS-записи выпуск
сертификата Let's Encrypt не пройдёт.

## Шаг 2. Каталог данных на сервере

Подключитесь по SSH и создайте каталог, в который позже приедет датасет:

```bash
ssh root@37.27.214.42 'mkdir -p /data/az700/images && chmod -R 777 /data/az700'
```

Права `777` нужны потому, что контейнер работает не от root (uid 1000), а
kubelet при первом создании тома создаёт каталог от root с правами `755` —
без ручного `chmod` SQLite не сможет открыть файл базы на запись. Тот же
приём уже используется в `kuber.sh` для `/data/postgres` и
`/opt/traefik-data`.

## Шаг 3. Перенос датасета

Скопируйте базу и картинки с вашей машины на сервер (~169 МБ, пара минут):

```bash
scp sample/data/az700.sqlite    root@37.27.214.42:/data/az700/
scp -r sample/data/images/*.png root@37.27.214.42:/data/az700/images/
```

Каталог `/data/az700` уже входит в существующий `files_backup.sh` (он
архивирует всё под `/data`), так что отдельно настраивать резервное
копирование не нужно.

## Шаг 4. Секрет сессии

Приложение подписывает cookie сессии ключом, который должен быть постоянным
(иначе при каждом перезапуске пода все входы слетают). Сгенерируйте значение:

```cmd
python -c "import secrets; print(secrets.token_hex(32))"
```

Скопируйте `deploy/k3s/az700-secret.example.yaml` в `deploy/k3s/az700-secret.yaml`
(это имя уже в `.gitignore` — файл с реальным ключом никогда не попадёт в
git) и вставьте сгенерированное значение вместо `<SECRET>`. Затем скопируйте
файл на сервер, например в `~/az700/az700-secret.yaml`.

## Шаг 5. Манифесты

Скопируйте на сервер весь каталог `deploy/k3s/` (кроме `.example.yaml`), например
через `scp -r deploy/k3s root@37.27.214.42:~/az700`, и на сервере выполните:

```bash
cd ~/az700
./install.sh
```

Скрипт применяет манифесты по порядку, с паузой между ними:

| Файл | Что создаёт | Зачем |
|---|---|---|
| `az700-storage.yaml` | `PersistentVolume` + `PersistentVolumeClaim` | Подключает `/data/az700` как том пода |
| `az700-secret.yaml` | `Secret` с ключом сессии | Ключ подписи cookie, не в образе и не в git |
| `az700-app.yaml` | `Deployment` + `Service` | Сам под приложения и его внутренний адрес в кластере |
| `az700-ingress.yaml` | `Ingress` | Маршрут `az700.v1.lv` → сервис, HTTPS через Traefik |

Под получает `priorityClassName: low-priority` (как и все ваши сайты, кроме
CIP) и небольшие запросы ресурсов (`50m` CPU / `128Mi` памяти) — свободного
резерва на ноде немного, и это гарантированно в него укладывается.

Если когда-нибудь захотите закрепить эти файлы в вашем ansible-репозитории
`myk3s`, по образцу остальных приложений это означает: скопировать
`az700-*.yaml` в `ansible/files/mywebs/`, добавить `az700.v1.lv.sh` в
`ansible/files/mywebs_install/` и `mywebs_uninstall/` (по образцу
`zaharov.info.sh`), и добавить три соответствующие записи в
`files_to_deploy` в `ansible/playbooks/site.yml`. Это необязательный шаг —
`install.sh`/`uninstall.sh` в этом репозитории работают и без него.

## Проверка

1. Под запустился и прошёл проверку готовности:
   ```bash
   k3s kubectl -n mywebs get pod,svc,ingress -l app=az700
   ```
   Ожидается `1/1 Running`.

2. Приложение отвечает и сертификат выпущен:
   ```bash
   curl -I https://az700.v1.lv/healthz
   ```
   Ожидается `HTTP/2 200`, без предупреждений о сертификате.

3. Откройте `https://az700.v1.lv` в браузере (и на телефоне), войдите под
   логином `dima`, убедитесь, что главное меню показывает
   «Доступно вопросов: 297 из 369» (или близкое число — зависит от того,
   сколько вопросов вы успели пометить некорректными на момент переноса).

4. Логи приложения при необходимости:
   ```bash
   k3s kubectl -n mywebs logs deploy/az700
   ```
   Каждая строка помечена `[RunId: xxxxxxx]` — этим идентификатором удобно
   искать записи одного конкретного запуска.

## Обновление приложения

Никаких ручных действий с манифестами не требуется. Обновление — это:

1. `git push` в `main` этого репозитория.
2. Дождаться зелёного workflow в GitHub Actions (тесты → сборка → публикация
   `ghcr.io/divlv/exam700:latest`).
3. На сервере перезапустить под, чтобы он подтянул новый образ:
   ```bash
   drestart az700
   ```
   (это ваш существующий алиас для `k3s kubectl -n mywebs rollout restart deployment`;
   эквивалент: `k3s kubectl -n mywebs rollout restart deployment/az700`).

Манифест использует тег `:latest` с `imagePullPolicy: Always`, так что новый
под всегда тянет самый свежий образ при перезапуске.

## Удаление

```bash
cd ~/az700
./uninstall.sh
```

Удаляет под, сервис, ingress, секрет и объекты тома. `PersistentVolume`
создан с `persistentVolumeReclaimPolicy: Retain`, поэтому сами данные в
`/data/az700` на диске сервера остаются нетронутыми — при повторной
установке ничего заново переносить не придётся.

## Диагностика

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| Под в `Pending` | На ноде не хватило запрошенной памяти/CPU | `k3s kubectl -n mywebs describe pod -l app=az700` — секция Events |
| Сертификат не выпускается / предупреждение браузера | DNS-запись ещё не завела, или завела недавно | `nslookup az700.v1.lv`, логи Traefik (`tl` / `k3straefiklogs`) |
| `unable to open database file` в логах | Права на `/data/az700` не выставлены | Повторить `chmod -R 777 /data/az700` на сервере, перезапустить под |
| `ImagePullBackOff` | Пакет в GHCR остался приватным | В настройках пакета на GitHub переключить видимость на Public |
| После входа сразу разлогинивает | `az700-secret.yaml` не применён или под перезапустился без него | `k3s kubectl -n mywebs get secret az700-secrets`, проверить, что `az700-app.yaml` ссылается на тот же секрет |
