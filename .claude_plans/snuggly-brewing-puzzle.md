# Безопасность: ключ Azure OpenAI в зашифрованном виде и логин из секретов

## Context

Репозиторий и Docker-образ публичные, приложение открыто в интернет. Два слабых места:

1. **Ключ Azure OpenAI** лежит в K8s Secret открытым текстом (и виден в `env` пода). В репозиторий и образ он не попадает, но на K3s нет шифрования Secret «на диске», и хочется, чтобы открытого ключа не было ни в манифестах, ни в переменных окружения.
2. **Логин `dima`** зашит в код, а код публичный. Пароля нет, значит войти и нажимать платную кнопку «AI» может любой, кто найдёт `az700.v1.lv`.

Решения пользователя: ключ шифруется, шифртекст в `AZURE_OPENAI_API_KEY_ENCRYPTED`, ключ расшифровки в `AZURE_OPENAI_API_KEY_DECRYPTION_KEY` и лежит в **отдельном Secret** (`az700-ai-key`); логин берётся из секрета, для локальных тестов из переменной `AZ_700_LOGIN`; ограничение трат кодом не нужно.

### Честный ответ на «увеличит ли это безопасность»

Само по себе шифрование почти ничего не даёт, пока шифртекст и ключ расшифровки лежат вместе: тот, кто прочитал Secret или зашёл в под, получает оба. Чтобы приложение расшифровало ключ, оно само должно получить ключ расшифровки, то есть открытый секрет остаётся, просто другой. Польза есть только от **раздельного хранения**:

| Угроза | Защищает ли выбранная схема (отдельный Secret) |
|---|---|
| Читатель публичного репозитория или образа | Уже защищены сейчас (ключа там нет); шифрование ничего не добавляет |
| Утечка файла `az700-secret.yaml`, копии манифестов, вывода `get secret az700-secrets`, вставленного в чат | **Да**: в них только шифртекст |
| Утечка файла хранилища K3s или его бэкапа (оба Secret лежат в нём) | **Нет**: там оба значения. Защитил бы только ключ расшифровки в файле на диске хоста вне K8s; в этот план не входит, в инструкции описываю словами |
| `kubectl exec` / root на сервере / доступ к кластеру | **Нет**: приложение работает с открытым ключом в памяти |

Сильнее шифрования работают меры на стороне Azure; их кодом не сделать, но опишу в инструкции: IP-правило на ресурсе Azure OpenAI только для `37.27.214.42` (проверено по Microsoft Learn: «Selected networks», одиночные публичные IPv4 или CIDR, до 100 правил; после включения Playground в браузере работает только с добавленного IP), отдельный ключ под это приложение с ротацией (Key 1/Key 2), лимит квоты на развёртывании, бюджетный алерт.

Логин из секрета фактически превращается в пароль в поле «Логин», поэтому он должен быть длинным случайным значением. Лимита числа попыток входа нет, при ≥ 24 случайных символах подбор нереален; при желании это отдельная задача.

## 1. Шифрование ключа (модуль `api/modules/aiassist/`)

Библиотека `cryptography` (Fernet: AES-128-CBC + HMAC-SHA256, аутентифицированное шифрование; ключ 32 байта в urlsafe-base64). Проверено по PyPI: 50.0.2 имеет готовые колёса `cp311-abi3` для Windows и `manylinux_2_28` x86_64, на Python 3.14 и в образе `python:3.14-slim` ставится без компиляции. `requirements.txt` += `cryptography>=44`.

- **Новый `internal/_secret.py`**: `generate_key()`, `encrypt(plaintext, key) -> token`, `decrypt(token, key) -> str`. Пробелы и перевод строки по краям значения игнорируются (файл и Secret могут добавить `\n`). При неверном ключе, битом или пустом значении выбрасывается `AiNotConfigured` с безопасным текстом (имена переменных, без значений).
- **`internal/_client.py`, `load_config()`**: если задан `AZURE_OPENAI_API_KEY_ENCRYPTED`, требуется и `AZURE_OPENAI_API_KEY_DECRYPTION_KEY`, ключ расшифровывается; иначе как раньше берётся `AZURE_OPENAI_API_KEY` (локальная разработка и текущие развёртывания не ломаются); **зашифрованный вариант приоритетнее**, при обоих сразу в стартовый лог пишется предупреждение «открытый ключ игнорируется, уберите его». Расшифровка идёт на каждый вызов `load_config` (микросекунды), так что неверный ключ виден сразу при старте. `redact()` дополнительно вырезает значения обеих новых переменных; `AzureConfig.__repr__` по-прежнему без ключа.
- **`api.py`**: наружу `encrypt_secret`, `generate_decryption_key`, константы имён переменных.
- **Новый CLI `api/modules/aiassist/keytool.py`** (запуск `python -m api.modules.aiassist.keytool` из корня репозитория, логика в `main(argv)` для тестов):
  - `generate --out-dir DIR [--from-env NAME]`: ключ Azure читается скрытым вводом (`getpass`) или из переменной окружения, генерируется ключ расшифровки; пишутся два файла `az700-ai-key.encrypted` и `az700-ai-key.decryption-key` (без перезаписи существующих; `.decryption-key` без перевода строки); перед выходом проверяется расшифровка туда-обратно; в консоль выводятся пути, шифртекст (по выбранной схеме он не секретен) и следующие шаги, **ключ расшифровки и открытый ключ не печатаются никогда**;
  - `check --encrypted-file F --key-file F`: расшифровывает и пишет только «OK, N символов» либо понятную ошибку, код возврата 0/1.
- `.gitignore`: `az700-ai-key.*`.

## 2. Логин из секрета (`web/`)

- **Новый `web/credentials.py`** (единое место, вместо константы `AUTHORIZED_LOGIN` в `deps.py`): читает `AZ_700_LOGIN` из окружения при каждом обращении (удобно для тестов), `login_matches(candidate)` через `hmac.compare_digest` по байтам UTF-8 (регистр важен, края обрезаются), `session_token()` = `sha256(login)` в hex.
  Имя переменной взято точно как написал пользователь (`AZ_700_LOGIN`, с подчёркиванием между AZ и 700); остальные переменные проекта называются `AZ700_*`: если это опечатка, замена сводится к одной константе.
- **Cookie сессии хранит не сам логин, а его отпечаток** (`SessionMiddleware` лишь подписывает cookie, содержимое читается). Побочный плюс: смена `AZ_700_LOGIN` и перезапуск разлогинивают все старые сессии.
- **`web/deps.py` `require_login`** и **`web/auth.py`** (GET/POST `/login`) сравнивают отпечаток; в cookie больше нет `dima`.
- **Не настроено (`AZ_700_LOGIN` пуст или не задан): вход закрыт для всех** (fail closed). Процесс не падает (`/healthz` жив, под не уходит в CrashLoop), страница входа показывает «Вход не настроен на сервере» (503), в стартовом логе строка уровня ERROR. Тихого запасного значения `dima` нет.
- Неудачная попытка входа пишется в лог (WARNING: IP клиента, **без введённого значения**); успешный вход INFO.
- **`login.html`**: поле становится `type="password"` (не светить секрет на экране), `autocomplete="current-password"`, `autocapitalize="off"`, `autocorrect="off"`, `spellcheck="false"` (иначе телефон делает первую букву заглавной, а сравнение теперь регистрозависимое).
- **`web/main.py`**: стартовые строки `ai=on deployment=… key=encrypted|plain` и `auth: login=configured|NOT SET` (значения не печатаются).

## 3. Манифесты, инструкция, ledger

- `deploy/k3s/az700-app.yaml`: `AZURE_OPENAI_API_KEY` заменяется на `AZURE_OPENAI_API_KEY_ENCRYPTED` (Secret `az700-secrets`, ключ того же имени) и `AZURE_OPENAI_API_KEY_DECRYPTION_KEY` (Secret `az700-ai-key`, ключ `DECRYPTION_KEY`); добавляется `AZ_700_LOGIN` (Secret `az700-secrets`, ключ `LOGIN`). Все `optional: true`: под стартует и без них (AI выключен, вход закрыт с понятным сообщением). Стратегия деплоя `Recreate`, поэтому не делаю их обязательными, чтобы пропущенный ключ не превращался в простой.
- `az700-secret.example.yaml`: плейсхолдеры `LOGIN`, `AZURE_OPENAI_API_KEY_ENCRYPTED`; открытого `AZURE_OPENAI_API_KEY` в примере больше нет.
- `install.sh`: в шапке предусловие «Secret `az700-ai-key` создан вручную»; `uninstall.sh`: `k3s kubectl -n mywebs delete secret az700-ai-key --ignore-not-found`.
- **`docs/deploy-k3s.md`** (обновляю существующий раздел про кнопку AI, дублей не создаю): таблица «что защищает и что нет» (из раздела выше); пошаговая инструкция:
  1. сгенерировать логин (`python -c "import secrets; print(secrets.token_urlsafe(18))"`), убрать в менеджер паролей;
  2. `python -m api.modules.aiassist.keytool generate --out-dir C:\tmp\az700-keys` и `... check ...`;
  3. вписать шифртекст и логин в `az700-secret.yaml`; открытый `AZURE_OPENAI_API_KEY` убрать. Нюанс: удаление ключа из `stringData` не удаляет его из уже существующего Secret, поэтому `k3s kubectl -n mywebs delete secret az700-secrets`, затем `apply -f az700-secret.yaml`; проверка без печати значений: `get secret az700-secrets -o jsonpath='{.data}' | jq 'keys'`;
  4. `scp` файла `az700-ai-key.decryption-key` на сервер, `k3s kubectl -n mywebs create secret generic az700-ai-key --from-file=DECRYPTION_KEY=az700-ai-key.decryption-key`, затем удалить файл на сервере (`shred -u`) и локально;
  5. применить `az700-app.yaml`, `git push`, дождаться образа, `drestart az700`;
  6. в логе пода `ai=on … key=encrypted` и `auth: login=configured`; вход с новым логином;
  - ротация (новый ключ в Azure → повторить п. 2–4), рекомендации по Azure (IP-правило, ротация, квота, бюджет), «как усилить дальше» (ключ расшифровки файлом на хосте, ссылка на `k3s secrets-encrypt` из документации SUSE: упоминается в v1.21.8+k3s1 и выше, точная версия появления флага в поиске не подтвердилась).
- Диагностика: строки про «AI не настроен» дополняются причиной «не расшифровывается: неверный ключ расшифровки», строка про «Вход не настроен».
- `CONTINUITY.md` (логин `dima` больше не хардкод; новая схема ключа и логина, порядок выкладки), `CONTEXT.md` (термины **Encrypted API key**, **Login secret**).

## Порядок выкладки (чтобы не заблокировать себя)

Новый образ при пустом `AZ_700_LOGIN` пускает **никого**, поэтому до `drestart`: Secret с `LOGIN` и шифртекстом обновлён, `az700-ai-key` создан, `az700-app.yaml` применён (он безопасен и для старого образа). Это же выписано в инструкции первым пунктом.
